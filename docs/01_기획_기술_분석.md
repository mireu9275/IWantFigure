# IWantFigure — 크레인게임 AI 조준 추천 앱 기획·기술 분석

- 작성일: 2026-09-24
- 한 줄 설명: 일본 게임센터 크레인게임(クレーンゲーム / UFOキャッチャー) 기계를 스마트폰으로 찍으면 AI가 경품 배치 유형을 인식하고 "어디를 노려야 하는지"를 3D로 보여주는 iOS/Android 앱을, C#/Kotlin 경험이 있는 1인 개발자가 어떻게 만들지 분석한 문서.

> **이 문서의 신뢰도에 대해 먼저**
> 이 분석은 5개 영역(도메인 지식 / 컴퓨터 비전·3D / 크로스플랫폼 / 시장·정책 / LLM)을 각각 별도 리서치로 조사하고, 그중 핵심 주장 12건을 1차 출처로 재검증한 결과를 합친 것이다. 조사 환경의 네트워크 정책 때문에 GitHub, pub.dev, npm, PyPI, Maven, NuGet, Anthropic 공식 문서, Apple 개발자 사이트 등은 원문을 직접 읽었지만, **일본 공략 사이트·스토어 페이지·JAIA·일본 언론 등 대부분의 일본어 사이트는 검색 결과 요약(스니펫)으로만 확인**했다. 스니펫 근거인 항목은 ★로 표시했고, 개발 착수 전에 재확인해야 할 목록을 15장에 모아 두었다. 라이브러리 버전·라이선스·API 가격처럼 원문을 확인한 항목은 ✅로 표시했다.

## 1. 한눈에 보기

1. **같은 컨셉의 앱이 이미 있다(★).** 일본에서 2026년 3월 「AIクレーンゲーム軍師 (AIClawCoach)」가 iOS/Android로 출시되어 "사진 촬영 → AI 해석 → 3Dパースガイ드로 조준점 표시"를 500엔/10회 티켓으로 팔고 있다. 스토어 페이지를 직접 열지는 못했으므로 **가장 먼저 실제 폰에서 설치해 확인**해야 한다. 차별화 없이는 시작하면 안 된다.
2. **추천 스택: Flutter(앱 셸·카메라·UI) + Filament 기반 3D(thermion_flutter) + 백엔드는 ASP.NET Core(C#).** Dart는 Kotlin/C# 개발자가 1~2주면 적응하고, Swift 없이 iOS까지 한 코드베이스로 간다. 라이브 AR 단계가 되면 Unity(C#) 씬을 `flutter_embed_unity`로 붙이는 것이 현실적 탈출구다.
3. **추천 파이프라인: 하이브리드.** 배치 유형 분류·전략·설명은 멀티모달 LLM(Gemini 3.8 Flash 또는 Claude Sonnet 5)에 맡기고, 조준 좌표는 LLM이 직접 찍게 하지 말고 **검출된 기하(상자·바·아암 박스) 위에서 룰 엔진이 계산**한다. 2026년 최고 VLM도 "점 찍기" 정확도가 사람 89% 대비 약 70%라(Point-Bench ✅) 좌표를 LLM에 맡기면 실패율이 높다.
4. **"3D 추천"은 사진의 3D 복원이 아니라 파라메트릭 씬이다.** 바 2개·상자 1개·아암·낙하구를 파라미터(위치·크기·자세)로 표현하고 3D로 렌더링해 조준 위치와 예상 움직임을 보여준다. 스케일은 알려진 상자 치수 + PnP로 잡고, 나중에 ARCore/ARKit 깊이로 보강한다.
5. **MVP 범위(2~3개월):** 사진 1장 → 유형 분류 + 2D 조준 오버레이 + 간단한 3D 씬(회전/줌) + 성공/실패 피드백. 온디바이스 검출기·AR은 v1/v2로 미룬다.
6. **가장 큰 리스크 3개:** (a) 선행 경쟁 앱과의 차별화 실패, (b) 유리 반사·조명·기종/설정(아암 파워는 사진에 안 보임) 때문에 정확도가 사용자 기대에 못 미침, (c) 게임센터 촬영 규정(タイトーステーション은 원칙 촬영 금지 ★)과 타인 얼굴 개인정보(APPI) 문제.
7. **데이터는 직접 만들어야 한다.** 크레인게임 사진 데이터셋은 공개된 것이 사실상 없다(GitHub·Roboflow 검색 ✅). 촬영 허용 체인(GiGO·ラウンドワン ★)에서 직접 찍고, 앱의 "사용자 보정"을 라벨링 루프로 설계한다.
8. **비용:** LLM 호출은 사진 1장당 $0.004~$0.04, 월 10만 회 기준 $400~$3,800(모델별, ✅ Claude 가격 / ★ Gemini·GPT 가격). 개발 고정비는 Apple $99/년 + Google $25 + Mac 확보(Mac mini M4 약 US$799 ★ 또는 Codemagic 무료 500분/월 ✅).
9. **법적 표현 가이드:** "반드시 획득" 표현 금지, 확률기 판정은 '추정'으로만, 특정 매장 비방 금지. 크레인게임 경품 상한은 경찰청 해석운용기준상 소매가 대체로 1,000엔 이하(2022-03-01 개정, 현행 유효 ✅).
10. **이번 주 할 일:** 경쟁 앱 설치·분석, 게임센터에서 사진 100장 촬영, Gemini/Claude에 프롬프트를 넣어 유형 분류 정확도 측정, thermion으로 3D 씬 PoC. 자세한 체크리스트는 14장.

## 2. 문제 정의

### 2.1 사용자 시나리오

| 단계 | 사용자 행동 | 앱 동작 | 제약 |
|---|---|---|---|
| ① 촬영 | 기계 정면(약간 위)에서 유리에 가깝게 1장 촬영. 필요하면 측면 1장 추가 | 촬영 가이드(정면·수평·유리 밀착), 얼굴 자동 블러, 흐림/반사 검사 | 대기 손님이 있으면 "1게임" 안에 끝내야 함(GiGO 규정 ★) → 촬영+해석 10초 이내 |
| ② 해석 | 기다림(3~8초) | 배치 유형 분류, 상자·바·아암·낙하구 검출, 스케일 추정, 룰 엔진으로 조준점 산출 | 서버 왕복 포함 8초 이내 목표 |
| ③ 추천 | 조준점·기법·예상 움직임 확인. 3D 씬을 돌려 봄 | 2D 오버레이(사진 위 마커·화살표) + 3D 파라메트릭 씬 + 텍스트 설명(한/일/영) | 좌표 근거를 항상 함께 표시(신뢰) |
| ④ 보정 | 상자 모서리·바 위치가 틀렸으면 손으로 끌어 수정 | 즉시 재계산. 보정값은 라벨 데이터로 저장(옵트인) | 보정 UX가 곧 데이터 수집 루프 |
| ⑤ 플레이 | 추천대로 플레이 | "움직였나/떴나/떨어졌나" 1탭 입력 → 아암 파워 추정 갱신, 다음 수 추천 | 매 플레이 재촬영 없이 진행 가능해야 함 |
| ⑥ 결과 | 성공/실패, 투입 금액 입력 | 기종·매장·경품별 통계, 커뮤니티 공유(옵션) | 얼굴 블러·매장명 공개 정책 필요 |

### 2.2 입력과 출력

- **입력:** 사진 1~3장(JPEG, 장변 1,000~2,000px로 클라이언트 리사이즈), 선택 입력(기종, 경품 이름/크기, 이전 플레이 관찰, 1플레이 요금).
- **출력(내부 표준 JSON):**
  - `layout_type`(橋渡し 평행/末広がり/段差, 前落とし, 谷落とし, ペラ輪, D環, S字フック, たこ焼き, 3本爪 직취, 2本爪 직취, 山積み, 直置き, 確率機 추정, unknown)
  - `scene`(2D: 정규화 0~1 좌표계의 상자·바·아암·낙하구 박스/키포인트, 3D: 아래 좌표계의 파라메트릭 씬)
  - `aim`(아암 중심의 목표 XY, 하강 목표, 어느 아암이 상자 어느 모서리에 걸리는지, 기법, 예상 움직임, 대안 2개, 철수 조건)
  - `explanation`(초보자용 한 문단), `confidence`, `needs_more_photos`, `warnings`

### 2.3 "3D 추천"이 실제로 의미하는 것

2D 오버레이는 "사진 위 이 지점"만 알려 준다. 3D 추천은 다음을 추가로 보여 준다.

- **아암이 내려올 XY 위치와 하강 깊이**(유리 정면에서 보면 안쪽/앞쪽 깊이가 안 보이므로 3D가 필요한 핵심 이유).
- **어느 발톱이 상자의 어느 모서리·변에 닿는지**와 그때 상자가 어느 축으로 회전하는지(예상 움직임 애니메이션).
- **낙하구까지의 경로**(몇 수에 걸쳐 어디로 옮길지).

이를 위해 사진을 진짜 3D로 복원할 필요는 없다. 크레인게임 필드는 정형 구조(평평한 필드 + 원기둥 바 2개 + 직육면체 상자 + 아암)이므로 **파라메트릭 씬**이면 충분하다.

**3D 좌표계(제안):** 원점 = 필드 바닥면 중앙, X = 플레이어 기준 오른쪽(+), Y = 플레이어 쪽(手前, +) / 안쪽(奥, −), Z = 위(+), 단위 mm. 카메라는 사진에서 추정한 외부 파라미터로 이 좌표계에 배치한다.

```json
{
  "machine": {"family": "UFO9_like", "field_size_mm": [700, 500], "claw_count": 2},
  "bars": [{"p0": [-120, -250, 80], "p1": [-120, 250, 80], "radius": 6, "material": "metal"},
           {"p0": [ 120, -250, 80], "p1": [ 120, 250, 80], "radius": 6, "material": "pink_tube"}],
  "prize": {"kind": "box", "size_mm": [150, 200, 100], "pose": {"t": [0, -20, 130], "rpy_deg": [0, 0, 5]},
            "com_offset_mm": [0, 0, -15], "mass_g_est": 250},
  "claw": {"type": "2claw", "open_width_mm": 180, "rest": [0, 300, 600]},
  "drop_hole": [[-90, -250], [90, -250], [90, 250], [-90, 250]],
  "aim": {"claw_xy_mm": [70, -95], "descent_z_mm": 135,
          "contact": {"arm": "right", "box_edge": "back_right_top"},
          "technique": "tate_hame", "expected_motion": "상자가 오른쪽 뒤 모서리를 축으로 약 25° 회전, 앞쪽이 바 사이로 내려감",
          "sequence": ["right→back_right", "left→front_left", "right→back_right"], "abort_if": ["3수 무변화", "가로+양바 얹힘(詰み)"]}
}
```

## 3. 도메인 지식 — 앱의 전략 룰베이스 초안

일본 공략 커뮤니티(SEGA 공식 공략, crane-game-party, curiousvv.jp, grabbit.co.jp, スマくれ, クレラボ 등 ★)의 지식을 정리했다. 원문을 직접 읽지 못했으므로 **수치와 "공식 권장" 표현은 출시 전 원문 재확인이 필요**하다(검증 결과: 관련 주장 3건이 '검증 불가'로 남음).

### 3.1 배치 패턴 → 인식 포인트 → 조준 전략 (룰베이스 표)

| # | 패턴 (日 / 韓) | 사진에서의 인식 포인트 | 노려야 할 위치·아암 | 표준 기법 | MVP 우선순위 |
|---|---|---|---|---|---|
| 1 | 橋渡し 평행형 (브릿지) | 박스 1개가 평행한 바 2개 위에 걸침, 바 간격 < 박스 긴 변 | 박스 중앙이 아니라 **한쪽 아암 발톱이 박스 끝에 아슬아슬하게 걸리는 위치**를 좌우 번갈아. 초기 위치가 안쪽으로 치우친 경우가 많아 手前부터. 무거운 박스 → 縦ハメ, 가벼운 박스 → 横ハメ(★ SEGA 공식 권장이라는 점은 미확인) | 縦ハメ, 横ハメ, ずり上げ, 角押し, 寄せ | **1순위**(피규어 박스의 표준 설정) |
| 2 | 橋渡し 末広がり / ハの字 | 바가 평행이 아니라 한쪽으로 벌어짐 | 넓은 쪽으로 회전·이동. 아암 파워가 약하면 잘 안 서므로 파워 확인이 우선. 강하면 つまみ上げ, 아니면 乗り上げ(양 아암으로 안쪽 모서리 들어 바 위에 얹기) | つまみ上げ, 乗り上げ | 1순위 |
| 3 | 橋渡し 段差 / クロス / ピンクチューブ | 두 바 높이가 다름 / X자 교차 / 바에 분홍·투명 고무 튜브(색으로 즉시 판별) | 段差: 높은 바에 비스듬히 기대 세운 뒤 ずり上げ. 튜브: 마찰이 커서 슬라이드 불가 → 들어올림·회전 계열로 전환 | ずり上げ, 乗り上げ | 2순위 |
| 4 | 前落とし | 박스가 필드 앞쪽, 낙하구가 플레이어 쪽 | 반대쪽 아암으로 끌어당기듯(寄せ) 좌우 번갈아 앞으로. 가벼운 쪽(보통 하반부)을 노리면 한 번에 많이 움직임. 충분히 오면 押し/持ち上げ | 寄せ, 押し込み, 持ち上げ | 1순위 |
| 5 | 谷落とし | V자 경사판, 틈이 낙하구 | 한쪽 경사면에 얹은 뒤 밀기. 가로로 완전히 끼면 詰み | 乗り上げ, 突き | 2순위 |
| 6 | 横落とし | 낙하구가 좌/우 측면 | 前落とし와 동일 원리로 측면 寄せ | 寄せ, 押し | 2순위 |
| 7 | ペラ輪 | 얇은 고리에 발톱을 넣어 끌어올림 | 구멍은 보기보다 작음 → 1수는 아암 개방폭 파악용 | 輪掛け, 寄せ | 3순위 |
| 8 | D環 / Oリング | 금속 링이 봉에 걸림 | 링 중심이 아니라 바깥쪽을 좌우 번갈아. 아암이 닫히는 동작으로 링을 움직임 | リング寄せ, 押し | 3순위 |
| 9 | S字フック(釣り) | 체인 + S자 훅 | 훅을 흔들어 링에 걸기(운 요소 큼) | 揺らし | 후순위 |
| 10 | たこ焼き | 핑퐁공 더미 + 구멍판 | 높게 쌓인 곳을 집기(운 요소) | — | 후순위 |
| 11 | 3本爪 ぬいぐるみ | 발톱 3개, 대형 인형, 대부분 확률기 ★ | 무게중심을 3발톱이 감싸도록. 태그 걸기. 임계 전엔 이동 기법만 유효 | バランスキャッチ, タグ掛け | 2순위 |
| 12 | 2本爪 직취 | 2발톱, 인형이 바닥/단 위 | 목·다리 사이·태그 등 걸릴 부위, 낙하구 쪽으로 寄せ | 引っ掛け, 持ち上げ | 2순위 |
| 13 | 山積み | 소형 경품 무더기 | 寄せる·押す·すくう, 눈사태(雪崩) 유도 | 雪崩, すくい | 후순위 |
| 14 | 箱 直置き | 박스가 바 없이 바닥·단 위 | 발톱 위치와 박스 틈이 맞도록. 大형은 横ハメ 후 角持ち上げ | 角持ち上げ | 2순위 |
| 15 | 確率機(추정) | 사진만으로 판별 불가. 3本爪·기종·アシストランプ 색으로 사전 확률만 | 임계 전엔 물리적 이동(確率無視)만. 발톱 휨·움직임 변화가 임계 신호 | 確率無視 | 판정 표시는 '추정'으로만 |

### 3.2 기법 용어집(UI 라벨·enum)

| enum | 용어 | 원리 |

### 3.5 조준 모델이 추론해야 할 물리 요소

1. **무게중심**: 뜨지 않는 쪽이 무거운 쪽. 무거운 쪽을 아래로 세우면 縦ハメ가 쉬움. 경품 DB(제품명 → 박스 치수·무게·무게중심)와 결합.
2. **바 마찰**: 금속(저마찰) vs 고무·분홍 튜브(고마찰). 고마찰이면 슬라이드 대신 들어올림·회전.
3. **박스 질량**: 프라이즈 박스 약 90~600 g ★. 아암 파워 대비 "들 수 있는가 / 기울일 수만 있는가" 판단.
4. **아암 폐쇄력·개방폭·발톱 각도**: 개방폭은 1수 관찰로 추정.
5. **하강 시 밀어내는 힘**: 押し·反動 계열의 근거.
6. **회전 모멘트**: 발톱을 박스 끝에 걸면 접촉점~무게중심 거리가 최대 → 최소 힘으로 최대 회전. 이것이 "端ギリギリ"와 ずらし의 원리이며, 룰 엔진의 핵심 수식이 된다.
7. **전도 조건**: 무게중심 연직선이 두 바 접촉선 밖으로 나가면 낙하. 縦ハメ는 지지폭을 단변으로 줄여 이 조건을 쉽게 만드는 것.

## 4. 기술 접근 옵션 비교

| 항목 | A) 클라우드 멀티모달 LLM 중심 | B) 온디바이스 CV(검출+깊이) 중심 | C) 하이브리드 (추천) |
|---|---|---|---|
| 구성 | 사진 → LLM이 유형·좌표·전략을 JSON으로 | 온디바이스 검출기(상자·바·아암)+깊이 → 룰 엔진 | LLM: 유형·전략·설명 / CV+룰 엔진: 기하·좌표 |
| 유형 분류 정확도 | 높음(언어적 추론, few-shot 효과 큼) | 학습 데이터 필요(초기엔 없음) | 높음 |
| 좌표 정확도 | 낮음(최상위 VLM 포인팅 ~70% ✅) | 높음(학습 후) | 초기: LLM bbox + 룰 / 후기: 검출기 + 룰 |
| 지연 | 3~8초 | <1초 | 3~8초 → 후기 1~3초 |
| 비용 | 회당 $0.004~0.04 | 0 | 회당 $0.004~0.02 |
| 오프라인 | 불가 | 가능 | 후기 일부 가능 |
| 개발 난이도(1인) | 낮음 | 높음(데이터셋·학습·모바일 배포) | 중간 → 단계적 상승 |
| 설명 가능성 | 높음(텍스트 근거) | 낮음 | 높음(룰 엔진 근거 + 텍스트) |
| 판정 | MVP 검증엔 최적, 좌표는 신뢰 불가 | 데이터 없이는 출발 불가 | **MVP는 A에 룰 엔진을 얹은 형태로 시작, 데이터가 쌓이면 B 요소를 추가** |

**추천: C.** 구체적으로 MVP에서는 LLM에게 (1) 유형, (2) 상자·바·아암·낙하구 **바운딩박스**(포인팅보다 검출이 안정적, Gemini는 `box_2d` 규약이 공식 ✅), (3) 기법·설명을 받고, **조준점은 앱의 룰 엔진이 박스 기하로부터 계산**한다. 사용자가 박스 모서리를 손으로 보정하면 즉시 재계산되며 그 보정이 라벨이 된다.

### 6.2 최종 추천과 근거

**1순위: Flutter 3.47 + thermion_flutter(대안 flutter_scene) + flutter_litert/tflite_flutter + camera.**
- 이유 ①: Swift를 배우지 않고 iOS까지 한 코드베이스로 출시할 수 있는 후보 중, Dart가 Kotlin/C# 개발자에게 가장 가깝다.
- 이유 ②: 이 앱의 3D는 "glTF 프리미티브 몇 개 + 마커 + 회전/줌"이라 Filament 기반 thermion으로 충분하다. PoC 2~3일이면 판단 가능하다.
- 이유 ③: 카메라·ML·얼굴 검출 플러그인이 모두 살아 있고, 일본·한국 커뮤니티가 가장 커서 막혔을 때 답을 찾기 쉽다.
- 약점과 대응: Android AR 플러그인이 죽어 있다. 라이브 AR(v2)은 `flutter_embed_unity`로 Unity AR Foundation 씬을 임베드(UaaL은 전체화면·단일 인스턴스·언로드 시에도 Android 90MB/iOS 110MB 상주 ✅)하거나, AR 화면만 Unity로 만든다.

**2순위: Unity 6.3 LTS + AR Foundation + Sentis (단독 앱).** C#을 그대로 쓰고 3D/AR/ONNX 추론이 한 프로젝트에서 해결된다. Personal은 연매출 US$200K 미만 무료 ★. 단 촬영 플로우·설정·다국어 같은 "앱 UI"를 Unity로 만드는 비용, 앱 용량, 스플래시가 부담. **처음부터 라이브 AR이 핵심 가치라면 이쪽.**

**3순위: KMP + Compose Multiplatform + SceneView(Android) + iOS는 UIKitView로 SceneKit.** Kotlin 강점을 살리지만 iOS 3D/AR을 Swift로 써야 해 iOS 경험 0인 현 시점에서는 병목. **Android 선출시, iOS 후속** 전략일 때만.

- 정지 사진 → 3D 추천을 6개월 내 양 플랫폼 출시: **Flutter**.
- 라이브 AR 오버레이가 1차 가치이고 C#을 버리기 싫다: **Unity 단독**.

| 아암 | 2/3발톱 단순 메시(개방폭) | 기종 프리셋, 1수 관찰로 개방폭 갱신 |
| 조준 마커 | 아암 중심 XY 원판 + 하강선 + 접촉 모서리 하이라이트 | 룰 엔진 |
| 예상 움직임 | 상자 회전·이동 애니메이션(1~3수) | 룰 엔진(모멘트·전도 조건) |

### 7.2 렌더링 라이브러리

- **thermion_flutter 0.5.0**(Google Filament 1.76 기반, Apache-2.0, iOS/Android/macOS/Windows/Web ✅): glTF·PBR·제스처 카메라. 첫 빌드에 네이티브 바이너리 다운로드.
- **flutter_scene 0.23.0**(Flutter GPU 기반, MIT, Flutter ≥3.47 필수, `--enable-flutter-gpu` ✅): pre-1.0이며 minor에 breaking 있음.
- 둘 다 개인 유지보수 pre-1.0 → **동일한 glTF 자산으로 2~3일 PoC 후 안정성이 좋은 쪽 선택**. 3D 자산은 Blender로 직접 만든 프리미티브(상자·원기둥·아암)면 충분하고, 기종 캐비닛은 실루엣 수준이면 된다(UFO CATCHER®는 SEGA 상표이므로 앱명·마케팅에 사용 금지 ★).

### 7.3 스케일(미터) 추정

1. **알려진 상자 치수 + PnP(권장, MVP):** 상자 앞면 4점 → OpenCV `solvePnP(IPPE_SQUARE)`. 프라이즈 박스 표준 치수 DB는 공개된 것이 없어(★) 직접 수집(경품명·시리즈별 폭/높이/깊이·무게). 사용자가 경품을 고르거나 "대략 20cm 피규어"만 선택해도 동작하게 한다.
2. **기종 치수:** 기종을 인식하면 필드 폭·바 간격 등 고정 치수로 보정(UFO CATCHER 10 1685×1050×1998 mm ★).
3. **ARCore Depth API(Android):** 16-bit mm, SDK 1.31부터 최대 65,535 mm, 1.56.0에 float 미터 API 추가, Raw Depth는 confidence 동반 ✅. 유리면까지의 거리·카메라 포즈 확보용.
4. **ARKit sceneDepth(iOS):** LiDAR 탑재 Pro 모델 전용, 256×192 @ 60 FPS, Float32 미터 + confidence ✅. Apple 문서는 고반사 표면에서 신뢰도 저하를 명시 → **유리 너머 경품 깊이의 주 소스로는 부적합**, RGB 경로를 기본으로.
5. **AR 세션 포즈:** ARKit/ARCore의 VIO가 미터 스케일 카메라 포즈를 주므로, AR 세션 안에서 2~3장을 찍으면 포즈 기지 다중뷰로 스케일 문제가 사라진다(v2).

### 7.4 AR 확장 경로

- v2에서 "카메라를 움직여도 조준 마커가 유리면 앵커에 붙어 있는" 라이브 오버레이를 목표로 한다.
- 구현: iOS `arkit_plugin`(활발 ✅) + Android/iOS 공통 `flutter_embed_unity`(AR Foundation) 또는 Android `SceneView`(Kotlin PlatformView).
- Apple 심사 4.2.1: AR 뷰에 모델을 "떨어뜨리기만" 하면 리젝 사유 ✅ → 조준선·거리 등 실질 기능을 갖춰야 한다.

### 8.6 정확도 확보 방법

1. **하이브리드 스냅:** LLM 좌표는 검출 박스 안으로 clamp, 룰 엔진이 최종 좌표 결정.
2. **사용자 보정 우선:** 모서리·바 드래그 → 즉시 재계산. 보정 빈도 자체가 인식 품질 지표.
3. **관찰 입력으로 베이지안 갱신:** 1수 후 "움직였다/떴다/안 움직였다" → 아암 파워·개방폭 추정 갱신 → 다음 수.
4. **self-consistency(유료):** 유형 다수결 + 좌표 중앙값, 불일치 시 추가 사진 요청.
5. **평가 세트:** 자체 라벨 100~300장으로 Claude/Gemini/Qwen3-VL A/B(유형 정확도, bbox IoU, 룰 엔진 조준점 오차 mm).

### 13.2 유사 도메인 AI 코치 앱의 UX(★)

- 당구 앱(AimBuddy US$1.99, Aim Master €9.99, DrillRoom AR+AI)은 **고스트볼 + 조준선**을 플레이어 시점에 그린다 → "고스트 아암 + 접촉 모서리 + 예상 경로" 3요소로 번역.
- 골프 퍼팅(Putt Vision US$4.99, GolfLogix 구독)은 **AR 지형 매핑 + 라인**.
- HomeCourt(농구)는 **무료 300샷/월 + US$7.99/월 무제한** — 카메라 앱의 표준 프리미엄 모델.

### 13.3 시장 규모(★ JAIA 원문 미열람)

- 일본 아뮤즈먼트 시장 2023년도 7,200억엔(오퍼레이션 5,384억엔, +4.7%), 2024년도 보고서는 매장 매출의 약 60% 이상이 프라이즈(크레인) 게임.
- 2025년 방일 한국인 945만 9,600명(+7.3%), 방일 외국인의 약 22%로 최대 시장. SEGA Fave가 2025-01 한국어 포함 5개 언어 게임센터 가이드에 크레인게임 팁 수록(인바운드 수요 공식 인정).
- 한국 뽑기방: 2026년 1분기 6,815곳, 인형뽑기방 매출 2024년 1,241억원 — 인형 중심이라 룰베이스가 달라짐(2차 시장).
